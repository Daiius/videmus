# 06. 認証と信頼モデル

## 1. 現状の方針: 「URL を知っていること」が権限

利用者は身内に限られ（[01](./01-experience.md) §2）、OAuth などのログインは大げさだと判断した。
そこで、**推測できない ID を知っていること自体を権限とする**（capability URL）。

| 知っているもの | できること |
|---|---|
| 何も知らない | `/broadcast` で新しい配信 ID を作れる（**無効の状態**で作られる） |
| 配信 ID（UUID v4） | 管理ページの閲覧、チャンネルの追加・名前変更・削除・選択、配信の状況の閲覧、OBS からの配信（有効なら）、配信の停止 |
| チャンネル ID（nanoid 21 文字。視聴用 URL に入る） | その配信の視聴、視聴者数の閲覧 |
| 管理者（DB への直接アクセス） | 配信 ID の有効化 |

- **配信 ID は配信者の身分証**。第三者に知られると配信を乗っ取られる。管理者以外には教えない。
  管理ページでは OBS 配信用 URL を最初は隠し、ダイアログで出すようにしている（誤って視聴者に送らないため）。
- **乱用への歯止めは管理者による有効化**。誰でも配信 ID は作れるが、有効化されるまで配信はできない。
- **API_KEY は next と resource-server の間だけ**のもの。DB の CRUD（[05](./05-api.md) §1.5）は Bearer を要求するが、
  next の Server Action はブラウザから呼べる。そのため実際の権限は「配信 ID を知っているかどうか」で決まり、
  API_KEY は resource-server を直接叩かれることを防ぐ層にとどまる。

## 2. 前提として守ること

- media-server の HTTP（内部 API を含む。[05](./05-api.md) §2）は外から直接届かないように配置する。
  外に出すのは resource-server と、WebRTC のポートだけ。
- 配信 ID を URL に含むページやログを、配信者と管理者以外に見せない。

## 3. 既知の弱点

| 弱点 | 影響 | 扱い |
|---|---|---|
| 配信 ID を誰でも何度でも作れる（回数の制限が無い） | 無効の配信 ID が DB に溜まりうる | 認証の導入（§4）で解消する |
| 視聴人数に上限が無い | 視聴用 URL が広まると、ホストの帯域を使い切りうる | 上限を入れる（[04](./04-media.md) §6）。gap |
| 配信の停止（`DELETE /whip/test-broadcast/:id`）と配信の状況の取得に、配信 ID 以外の認証が無い | 配信 ID を知られると止められる | 配信 ID を秘密にすることで守る。OBS の WHIP 経路にはブラウザのログインが効かないので、認証の導入後もここは配信者ごとの秘密で守る |
| チャンネルを削除しても視聴用 URL が失効しない | 一度 URL を渡した相手を後から締め出せない | 選択中のチャンネルを削除させないことで失効させる（[03](./03-data-model.md) §2.2）。gap |
| 配信 ID が管理ページの URL に入る | 画面共有やブラウザの履歴から漏れうる | 認証の導入（§4）で、管理ページを URL ではなくログインで守る |

## 4. 今後の方向: 認証の導入（近い将来）

当面は §1 の方針で運用し、近い将来に認証を入れる。

- **配信者にはログインを求める**（方針として決定）。配信 ID の作成・管理ページ・チャンネルの操作をアカウントに紐付け、
  今「秘密の配信 ID」が担っている役割をログインに移す。管理者による有効化も、DB の直接編集ではなく画面から行う。
- **OBS の配信用 URL には配信者ごとの秘密が残る**。WHIP はブラウザのログインを使えないため
  （URL の配信 ID、または Bearer トークン）。
- **視聴者のログインは検討中**（要確認）。視聴者を限定できる一方、「URL を送るだけで見られる」手軽さは失われる。
  パスキーのように手軽で強固なログイン手段なら、UX をそれほど損なわないと考えている。
- 認証の基盤には、他のリポジトリと同じく Better Auth を使う想定。DB の Postgres への移行（[03](./03-data-model.md) §2.3）も、
  このときにあわせて検討する。
