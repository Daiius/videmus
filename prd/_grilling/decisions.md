## 2024-10 ごろ: 開発メモ（MEMO.md）からの経緯

### 配信 ID を固定で割り当てる

- 配信のたびに異なる配信用 URL を OBS に設定するのは、セキュリティ面では良さそうだが面倒。
  配信者ごとに決まった ID を（基本的に）固定で割り当てる。
- OAuth で管理すれば利用者を増やせるが、身内だけで使うなら「ID を発行 → 先頭の数文字を教えてもらって手動で有効化」で足りる。

### チャンネルを設ける（2024-10-31）

- デモのとき、OBS が（おそらくフレームレートの低下で）切断・再接続し、視聴用 URL がリセットされた。
- 同じ視聴用 URL を使い回すと、ホラー系の配信を誤って開いた人を驚かせかねない。
- そこで、視聴用 URL を毎回作り直すのではなく、配信者ごとに「チャンネル」を持たせて視聴用 URL を管理する。
- チャンネルを切り替える方法は 2 案あった。①OBS に渡す URL や Bearer トークンをチャンネルごとに変える、
  ②Videmus の管理ページでチャンネルを選ぶ。**「1 人の配信者は同時に 1 配信しかしない」と仮定して ② を採った。**
  どのチャンネルに配信しているかを 1 つ設定するだけで済むため。
- media-server のリソースは配信 ID をキーに持っていて、視聴用 ID（streamId）は接続確立のための ID にすぎない。
  そのため、配信中でも視聴用 ID を書き換えればチャンネルを切り替えられ、すでに見ている視聴者は見続けられる。
  ただし、視聴者側で再接続するときには、切り替え後のチャンネルが分からないと接続できない。

### 配信 ID とチャンネルの相互参照

- 理想は、`BroadcastIds.current_channel` を not null の外部キーにすること（配信 ID は必ず 1 つ以上のチャンネルを持つ）。
- 互いを参照するので、挿入時に deferred constraint が要るが、MySQL には無い。
- DB 側の制約を緩め、アプリ側で担保する。`current_channel` を NULL のまま配信 ID を入れ、チャンネルを作ってから
  `current_channel` を設定する。使うときは毎回 NULL かを調べ、NULL なら既定値（最初に登録されたチャンネルなど）を入れる。
- チャンネルを消すときに外部参照が厳密すぎると扱いがややこしくなるので、ここもアプリ側で担保する。
  （→ 2026-10-22 時点で、選択中のチャンネルの削除が防げていない。[03](../03-data-model.md) §2.1）
